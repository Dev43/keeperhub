# 0G integration -- KeeperHub bridge

Internal spec for the 0G chain seeds and plugins shipped on `feature/0g-integration`. Lives in `specs/` because the docs site is public and this is a working doc; once the upstream PR lands we can decide whether any of it gets promoted into `docs/`.

## Surface added

1. **0G Galileo Testnet (chain ID 16602)** and **0G Mainnet (chain ID 16661)** wired into `lib/rpc/rpc-config.ts` and seeded by `scripts/seed/seed-chains.ts`. Symbol `0G`. Primary RPCs: `https://evmrpc-testnet.0g.ai` and `https://evmrpc.0g.ai`. Explorer: `https://chainscan-galileo.0g.ai` and `https://chainscan.0g.ai` (Blockscout-family API).
2. **`plugins/0g-storage`** -- three actions, all signed via the org's KeeperHub wallet (Para or Turnkey). `requiresCredentials: false`; the only configurable fields are chain id, indexer URL, and Flow contract address, all defaulted to Galileo:
   - `kv-get` -- read a KV value by data root hash. Pure HTTP against the public indexer; decodes the `StreamData` wire format inline so no self-hosted KV node is required.
   - `kv-put` -- write a KV value by submitting an on-chain Flow transaction. `maxRetries = 0`.
   - `log-append` -- append a tagged entry to an append-only log stream by uploading a signed blob. `maxRetries = 0`.
3. **`plugins/0g-compute`** -- three actions, also signed via the org's KeeperHub wallet through the `@0glabs/0g-serving-broker`. `requiresCredentials: false`; only the chain id is configurable:
   - `list-providers` -- enumerate serving providers (model, endpoint, address, pricing, verifiability), with optional substring filter.
   - `fund-provider` -- ensure the broker ledger has enough balance for a given provider, topping up from the org wallet only if needed. `maxRetries = 0`.
   - `inference` -- send a chat-completions request to a provider via the broker's signed-headers flow and verify the response. `maxRetries = 0`.
4. **`plugin-allowlist.json`** -- adds `0g-storage` and `0g-compute`.
5. **Generated by `pnpm discover-plugins`** -- updates to `lib/types/integration.ts`, `plugins/index.ts`, and the gitignored `lib/step-registry.ts` / `lib/codegen-registry.ts`.

## Implementation notes

- Both plugins use real 0G SDKs (`@0gfoundation/0g-ts-sdk` for storage, `@0glabs/0g-serving-broker` for compute) but sandbox them inside `*-core.ts` files so the workflow bundler does not pull SDK transitive deps into step bundles. Step files import a small surface from the core file and call `fetch()` directly for the actual provider HTTP request.
- Step files follow `plugins/CLAUDE.md` rules: only the step function, `_integrationType`, and types are exported; helpers live in `*-core.ts`.
- The org wallet abstraction is shared with the rest of the web3 plugins via `resolveOrganizationContext` from `@/lib/web3/resolve-org-context`. There are no plugin-specific private-key envs.
- 0G storage indexer URL defaults to `https://indexer-storage-testnet-turbo.0g.ai`; Flow contract defaults to the Galileo deployment. Both are overridable per-integration.
- The 0G compute broker initializes against the chain's primary RPC from `lib/rpc/rpc-config.ts`, so swapping between testnet and mainnet is a single chain-id change.

## Per-tx detection workflow shape (Phulax demo)

No new trigger or step type is introduced for the Phulax demo. Per-tx detection on the FakeLendingPool composes existing primitives:

1. `Block` trigger fires every block on chain 16602.
2. `web3/query-transactions` with `contractAddress = <FakeLendingPool>`, `fromBlock = toBlock = trigger.blockNumber` returns `0..N` decoded txs.
3. `0g-storage/kv-get` loads the latest exploit corpus by root hash.
4. `code/run-code` folds the array, calling the self-hosted classifier per tx and computing `maxScore`.
5. `0g-storage/log-append` writes a signed receipt to the per-account incident log.
6. `system/condition` gates on `maxScore > threshold`.
7. `web3/write-contract` (private mempool variant when available) calls `PhulaxAccount.withdraw(adapter)`.

Skeleton lives in `specs/0g-integration/per-tx-detection.workflow.json`.

## Why self-hosted classifier, not 0G compute, on the demo hot path

The `0g-compute` plugin ships in this PR for any KeeperHub user who wants to call a 0G-served base model from a workflow. The Phulax demo itself uses a self-hosted classifier endpoint (HTTP Request system action) because 0G sealed inference does not currently serve our LoRA-adapted Qwen2.5-0.5B. Verifiability for the demo is "publish-and-replay": merged weights and eval harness on 0G Storage, signed `(input_hash, output, model_hash)` receipts written to a 0G Storage log on every fire.
